# Documentation for PySpark Stroke Algorithm Implementation

## Overview

This project falls under the BHF Data Science Centre's [SCORE-CVD](https://zenodo.org/records/8171481) (Standardising Clinical Outcome measures in Routinely collected Electronic healthcare systems data) project. It provides a pipeline for identifying stroke events, including recurrent strokes, in HES APC and ONS deaths datasets. Priority is given to stroke events identified in HES APC records: if a stroke event is counted in HES records, the event is not counted again in the deaths records. A flowchart detailing the logic of the algorithm can be found in the docs folder `docs > flowchart`.

Following discussions around the different needs of projects, the algorithm has been developed to allow flexibility in certain parameters, for example the ICD10 codes used, the subtypes defined, the washout periods between first and subsequent stroke etc. These require user input in the 'parameters' notebook, otherwise default values will be run. 

The ICD-10 codes used to identify stroke events are configurable by the user in the `parameters` notebook. The default codes are:

| Subtype | ICD-10 codes |
|---------|-------------|
| Ischaemic | I63 |
| Haemorrhagic | I60, I61 |
| Unknown | I64 |

Stroke subtype is derived at episode level from the first stroke code identified in the diagnosis array, then harmonised to CIPS level: if more than one subtype is present within a single CIPS, the CIPS is labelled `"unknown"`.

Continuous inpatient spells were generated based on documentation from the [Health & Social Care Information Centre (2014)](https://webarchive.nationalarchives.gov.uk/ukgwa/20180307232845tf_/http:/content.digital.nhs.uk/media/11859/Provider-Spells-Methodology/pdf/Spells_Methodology.pdf).

This document provides documentation for the PySpark implementation of the SCORE-CVD Stroke detection algorithm in Databricks.

The algorithm processes HES APC and ONS deaths records to identify and classify stroke events using a decision tree approach.

### 3.1 parameters.py

This notebook defines all user-configurable parameters for the stroke algorithm. It is run at the top of each algorithm notebook. **Users should edit parameters here only** — not in the algorithm notebooks themselves.

#### Key parameters
The below table presents the default values which can be edited by the user. See 'parameters' notebook for detailed info on acceptable values for parameters.

| Parameter | Default | Description |
|-----------|---------|-------------|

```python

    "ischaemic":    ["I63"],
    "haemorrhagic": ["I60", "I61"],
    "unknown":      ["I64"]
```

### 3.2 D02-hes_apc_stroke_algorithm.py

This script implements the stroke detection algorithm for HES APC data.

#### Key Processing Steps

1. **Data preparation (section 2):** Loads `hes_apc_cips_episodes` and the study cohort. Selects episode columns, constructs diagnosis arrays for all relevant positions, filters to the study period, and joins to the cohort. Saved as `hes_apc_algo_prep`.

2. **Stroke code flagging and patient split (section 3):** Flags episodes with stroke codes in any relevant position (`diag_stroke_any`), valid first-stroke positions (`diag_first_stroke_positions`), and valid subsequent-stroke positions (`diag_subsequent_stroke_positions`). Creates a person-level flag (`individual_with_stroke`) using a window function. Splits into `hes_apc_algo_non_stroke_patients` (T0) and `hes_apc_algo_stroke_patients`.

3. **Stroke subtyping (section 4):** For individuals with at least one stroke code, extracts all stroke codes present in each episode's diagnosis array (`stroke_codes_in_episode`), identifies the first (`first_stroke_code`), and assigns an episode-level subtype (`stroke_type_episode`). Harmonises to CIPS level: where more than one distinct subtype is present within a CIPS, the CIPS-level subtype (`stroke_type_cips`) is set to `"unknown"`.

4. **Algorithm function definition (section 5):** Defines `hes_apc_stroke_pandas()`, a pandas UDF that processes each individual's episodes in chronological order, applying the decision tree row by row and assigning terminal nodes, stroke dates, stroke counts, and qualification flags.

5. **Algorithm application (section 6):** Applies `hes_apc_stroke_pandas()` grouped by `person_id` using `applyInPandas()`. Derives `recurrent_stroke` as a post-processing step (`stroke_count > 1`).

6. **Terminal node summary (section 7):** Displays episode and individual counts at each terminal node.

7. **Flowchart generation (section 8):** Constructs a full decision tree flowchart by evaluating each node's expression against the classified data, unpivoting to long format, and summarising counts. Saves both standard and SDC-rounded versions as CSV.

#### Derived Variables

##### diag_stroke_any
**Label:** Any stroke code flag  
**Description:** Whether the episode contains a stroke ICD-10 code in any relevant diagnosis position (union of first and subsequent positions)  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `array_intersect(diag_array_any, stroke_codes)` size > 0  
**Usage:** D1 — primary filter; separates stroke from non-stroke episodes

##### diag_first_stroke_positions
**Label:** Stroke code in valid first-stroke position flag  
**Description:** Whether a stroke code is present in one of the diagnosis positions specified for a first stroke event  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `array_intersect(diag_array_first_stroke_positions, stroke_codes)` size > 0  
**Usage:** D3 — determines whether a first-record stroke code is in a valid position

##### diag_subsequent_stroke_positions
**Label:** Stroke code in valid subsequent-stroke position flag  
**Description:** Whether a stroke code is present in one of the diagnosis positions specified for a subsequent stroke event  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `array_intersect(diag_array_subsequent_stroke_positions, stroke_codes)` size > 0  
**Usage:** D5 — determines whether a subsequent-record stroke code is in a valid position

##### individual_with_stroke
**Label:** Person-level stroke flag  
**Description:** Whether the individual has at least one episode with a stroke code in any relevant position, across the study period  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `max(diag_stroke_any)` over `person_id` window  
**Usage:** Used to split into stroke and non-stroke patient populations before applying the algorithm

##### stroke_codes_in_episode
**Label:** Stroke codes present in episode  
**Description:** Array of all stroke ICD-10 codes found in the episode's diagnosis array (any position). Filtered using a LIKE expression matching the stroke code prefixes.  
**Data type:** Array of strings  
**Values:** e.g. `["I63"]`, `["I60", "I61"]`, `[]`  
**Derivation:** `filter(diag_array_any, x -> x LIKE 'I60%' OR x LIKE 'I61%' OR ...)`  
**Usage:** Intermediate — used to derive `first_stroke_code`

##### first_stroke_code
**Label:** First stroke code in episode  
**Description:** The first stroke ICD-10 code identified in `stroke_codes_in_episode` (index 0). Used to assign episode-level subtype.  
**Data type:** String  
**Values:** e.g. `"I63"`, `"I60"`, null  
**Derivation:** `stroke_codes_in_episode[0]` when array is non-empty  
**Usage:** Input to episode-level subtype assignment

##### stroke_type_episode
**Label:** Episode-level stroke subtype  
**Description:** Stroke subtype derived from `first_stroke_code` using prefix matching against `stroke_subtype_map`. Set iteratively per subtype.  
**Data type:** String  
**Values:** `"ischaemic"`, `"haemorrhagic"`, `"unknown"`, null  
**Derivation:** `when(first_stroke_code.startswith(prefix), subtype)` for each entry in `stroke_subtype_map`  
**Usage:** Input to CIPS-level subtype harmonisation

##### stroke_types_in_cips
**Label:** Set of subtypes within CIPS  
**Description:** Distinct set of stroke subtypes observed across all episodes within the same CIPS, for that individual  
**Data type:** Array of strings  
**Values:** e.g. `["ischaemic"]`, `["ischaemic", "haemorrhagic"]`  
**Derivation:** `collect_set(stroke_type_episode)` over `(person_id, cips_id)` window  
**Usage:** Intermediate — used to derive `n_subtypes_cips` and `stroke_type_cips`

##### n_subtypes_cips
**Label:** Number of distinct subtypes in CIPS  
**Description:** Count of distinct stroke subtypes within the CIPS  
**Data type:** Integer  
**Values:** 0, 1, 2, 3  
**Derivation:** `size(stroke_types_in_cips)`  
**Usage:** Determines whether CIPS-level subtype is set to `"unknown"`

##### stroke_type_cips
**Label:** CIPS-level stroke subtype  
**Description:** Stroke subtype harmonised at CIPS level. Where more than one distinct subtype is present across episodes in a CIPS, the subtype is set to `"unknown"`.  
**Data type:** String  
**Values:** `"ischaemic"`, `"haemorrhagic"`, `"unknown"`, null  
**Derivation:** `when(n_subtypes_cips > 1, "unknown").otherwise(stroke_type_episode)`  
**Usage:** Primary stroke subtype output column for HES APC

##### qualify
**Label:** Stroke event qualification flag  
**Description:** Whether the episode qualifies as a stroke event according to the decision tree  
**Data type:** Boolean  
**Values:** True / False  
**Missing values:** False for non-qualifying episodes  
**Derivation:** Set within `hes_apc_stroke_pandas()` based on decision tree path (T3 and T7 only)  
**Usage:** Primary outcome — identifies qualifying stroke episodes

##### stroke_date
**Label:** Stroke event date  
**Description:** Date assigned to the qualifying stroke event. For both first (T3) and recurrent (T7) strokes, `stroke_date` is set to `epistart`. Note that the internal washout-tracking variable (`last_valid_stroke_date`) is set to `admidate` at T3, meaning washout periods for subsequent strokes are calculated from the admission date of the first stroke rather than its episode start date.  
**Data type:** Date  
**Missing values:** NaT for non-qualifying episodes  
**Derivation:** Set within `hes_apc_stroke_pandas()`: `pdf.at[index, 'stroke_date'] = row['epistart']` at both T3 and T7  
**Usage:** Temporal reference for the stroke event; used in ONS deaths washout logic

##### stroke_count
**Label:** Stroke event index  
**Description:** Sequential count of qualifying stroke events for the individual. Increments by 1 for each new qualifying stroke.  
**Data type:** Integer  
**Values:** 1 (first stroke), 2, 3, ... (recurrent strokes); 0 for non-qualifying episodes  
**Derivation:** `stroke_counter` incremented within `hes_apc_stroke_pandas()` at T3 and T7  
**Usage:** Identifies first versus recurrent stroke events

##### first_stroke_diagnosis
**Label:** First stroke diagnosis flag  
**Description:** Whether this episode is the qualifying first stroke event for the individual (terminal node T3)  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** Set to True at T3 within `hes_apc_stroke_pandas()`  
**Usage:** Distinguishes the first qualifying stroke from subsequent ones

##### recurrent_stroke
**Label:** Recurrent stroke flag  
**Description:** Whether the qualifying stroke event is a recurrent (subsequent) event  
**Data type:** Boolean  
**Values:** True (stroke_count > 1) / False (first stroke) / null (non-qualifying)  
**Derivation:** `stroke_count > 1` applied as a post-processing `withColumn()` after `applyInPandas()`  
**Usage:** Epidemiological classification of first versus recurrent stroke events

##### same_cips_as_last_stroke
**Label:** Same CIPS as last stroke flag  
**Description:** Whether this episode is part of the same CIPS as the most recent qualifying stroke event  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `row['cips_id'] == last_valid_cips` within `hes_apc_stroke_pandas()`  
**Usage:** D4 — episodes in the same CIPS as the last stroke are excluded (T4)

##### terminal_node
**Label:** Decision tree terminal node  
**Description:** The terminal node reached for this episode in the HES APC stroke decision tree  
**Data type:** Integer  
**Values:** 0–7 (see decision tree section)  
**Missing values:** None  
**Derivation:** Set within `hes_apc_stroke_pandas()` or as a literal for T0  
**Usage:** Audit trail and flowchart generation

##### terminal_node_description
**Label:** Terminal node description  
**Description:** Plain-text description of the terminal node reached  
**Data type:** String  
**Values:** See decision tree section  
**Derivation:** Set within `hes_apc_stroke_pandas()` or as a literal for T0  
**Usage:** Audit trail and human-readable reporting

### 3.3 D03-ons_deaths_stroke_algorithm.py

This script implements the stroke detection algorithm for ONS deaths data.

#### Key Processing Steps

1. **Data preparation (section 2):** Loads `ons_deaths_cleaned` and the study cohort. Truncates ICD-10 codes in all relevant death certificate columns to the length specified by `icd10_code_length_deaths`. Constructs death arrays for all positions, first-stroke positions, and subsequent-stroke positions. Filters to study period and joins to cohort.

2. **Stroke code flagging and patient split (section 3):** Flags death records with stroke codes in any relevant position (`death_stroke_any`), valid first-stroke positions (`death_first_stroke_positions`), and valid subsequent-stroke positions (`death_subsequent_stroke_positions`). Creates a person-level flag (`individual_with_stroke_death`) and splits into non-stroke deaths (T0) and stroke deaths for further classification.

3. **Stroke subtyping (section 4):** Extracts all stroke codes from the death record's array (`stroke_codes_in_death_episode`), identifies the first (`first_stroke_code_death`), and assigns a death-episode-level subtype (`stroke_type_death_episode`) using prefix matching against `stroke_subtype_map`.

4. **In-hospital death flagging (section 5):** Joins to `hes_apc_cleaned` to identify deaths that occurred in hospital (discharge within 1 day of death AND `dismeth = "4"` OR `disdest = "79"`, OR death date before `pmax(epiend, disdate)` with discharge-to-death flag). Aggregated to person level as `in_hospital_death`.

5. **Washout period and prior HES stroke flagging (section 6):** Joins to qualifying HES APC stroke events to calculate days between death and each prior stroke. Flags deaths within the washout window (`stroke_within_washout`) and whether any prior qualifying HES stroke exists at all (`prior_qualifying_hes_stroke`).

6. **Decision tree application (section 7–8):** Joins `in_hospital_death` and `prior_hes_stroke` flags to the stroke deaths. Derives `qualify` and `stroke_date` using the decision tree logic.

7. **Flowchart generation (section 9):** Constructs and saves the full ONS deaths decision tree flowchart, with SDC-rounded version.

#### Derived Variables

##### death_stroke_any
**Label:** Any stroke code in death record flag  
**Description:** Whether the death record contains a stroke ICD-10 code in any relevant death certificate position (union of first and subsequent positions)  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `array_intersect(death_array_any, stroke_codes)` size > 0  
**Usage:** Primary filter — separates stroke from non-stroke deaths

##### death_first_stroke_positions
**Label:** Stroke code in valid first-stroke death position flag  
**Description:** Whether a stroke code is present in one of the death certificate positions specified for a first stroke death  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `array_intersect(death_array_first_stroke_positions, stroke_codes)` size > 0  
**Usage:** D4 — used when no prior HES stroke exists

##### death_subsequent_stroke_positions
**Label:** Stroke code in valid subsequent-stroke death position flag  
**Description:** Whether a stroke code is present in one of the death certificate positions specified for a subsequent stroke death  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `array_intersect(death_array_subsequent_stroke_positions, stroke_codes)` size > 0  
**Usage:** D5 — used when a prior qualifying HES stroke exists

##### individual_with_stroke_death
**Label:** Person-level stroke death flag  
**Description:** Whether the individual has at least one death record with a stroke code in any relevant position  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `max(death_stroke_any)` over `person_id` window  
**Usage:** Splits into stroke and non-stroke death populations

##### stroke_codes_in_death_episode
**Label:** Stroke codes present in death record  
**Description:** Array of all stroke ICD-10 codes found in the death record's combined cause-of-death array  
**Data type:** Array of strings  
**Values:** e.g. `["I63"]`, `["I60"]`  
**Derivation:** `filter(death_array_any, x -> x LIKE 'I60%' OR ...)`  
**Usage:** Intermediate — used to derive `first_stroke_code_death`

##### first_stroke_code_death
**Label:** First stroke code in death record  
**Description:** The first stroke ICD-10 code identified in `stroke_codes_in_death_episode` (index 0)  
**Data type:** String  
**Values:** e.g. `"I63"`, `"I60"`, null  
**Derivation:** `stroke_codes_in_death_episode[0]` when array is non-empty

##### stroke_type_death_episode
**Label:** Death episode stroke subtype  
**Description:** Stroke subtype derived from `first_stroke_code_death` using prefix matching against `stroke_subtype_map`  
**Data type:** String  
**Values:** `"ischaemic"`, `"haemorrhagic"`, `"unknown"`, null  
**Derivation:** `when(first_stroke_code_death.startswith(prefix), subtype)` for each entry in `stroke_subtype_map`  
**Usage:** Stroke subtype output for ONS deaths

##### in_hospital_death
**Label:** In-hospital death flag  
**Description:** Whether the individual's death is recorded as occurring in hospital, based on linkage to HES APC. Defined as: (discharge date within 1 day of death AND dismeth = `"4"` OR disdest = `"79"`) OR (death date before `pmax(epiend, disdate)` AND discharge-to-death flag).  
**Data type:** Boolean  
**Values:** True / False  
**Missing values:** False when no HES APC record found  
**Derivation:** Derived from HES APC join; aggregated as `max(in_hospital_death)` per person  
**Usage:** D1 — in-hospital deaths are excluded (T1) as they are captured by the HES APC algorithm

##### stroke_within_washout
**Label:** Stroke within washout period flag  
**Description:** Whether the individual had a qualifying HES APC stroke within `washout_between_death_and_hes_stroke` days before the death date  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `days_between >= 0 AND days_between < washout_between_death_and_hes_stroke`; aggregated as `max()` per person  
**Usage:** D2 — deaths within the washout period of a prior HES stroke are excluded (T2)

##### prior_qualifying_hes_stroke
**Label:** Prior qualifying HES stroke flag  
**Description:** Whether the individual had any qualifying stroke event in HES APC prior to death (regardless of washout)  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `max(when(stroke_date IS NOT NULL, True).otherwise(False))` per person, from left join to qualifying HES strokes  
**Usage:** D3 — determines whether first-stroke or subsequent-stroke death certificate positions are applied

##### qualify
**Label:** Stroke death qualification flag  
**Description:** Whether the death record qualifies as a stroke event  
**Data type:** Boolean  
**Values:** True / False  
**Derivation:** `NOT in_hospital_death AND NOT stroke_within_washout AND ((NOT prior_qualifying_hes_stroke AND death_first_stroke_positions) OR (prior_qualifying_hes_stroke AND death_subsequent_stroke_positions))`  
**Usage:** Primary outcome — identifies qualifying stroke deaths

##### stroke_date
**Label:** Stroke event date  
**Description:** Date assigned to the qualifying stroke death event  
**Data type:** Date  
**Values:** Equal to `date_of_death` for qualifying records  
**Missing values:** Null for non-qualifying records  
**Derivation:** `stroke_date = date_of_death`  
**Usage:** Temporal reference for the stroke event in combined events table

##### terminal_node (ONS deaths)
**Label:** Decision tree terminal node  
**Description:** The terminal node reached for this death record in the ONS deaths stroke decision tree  
**Data type:** Integer  
**Values:** 0–6 (see decision tree section)  
**Derivation:** Derived from the `flowchart_schema` node expressions applied to the classified data  
**Usage:** Audit trail and flowchart generation

## 4. Algorithm Decision Tree Logic
Flowchart of algorithm logic is available to view in the docs folder `docs > flowchart`.

### Part A: HES APC algorithm

The HES APC stroke detection algorithm applies the following logic to each episode, processed chronologically per individual:

| Node | Description |
|------|-------------|
| **D1** | Does this episode contain a stroke ICD-10 code in any relevant diagnosis position? |
| **T1** | No → Not a stroke event |
| **D2** | Is this the first record with a stroke code for this individual (no prior qualifying stroke)? |
| **D3** | First record: is the code in a valid position for a **first** stroke (as defined in `code_positions_first_stroke_hes_apc`)? |
| **T2** | No → Not a stroke event — code not in valid first-stroke position |
| **T3** | Yes → **First stroke event** |
| **D4** | Subsequent record: is this episode part of the same CIPS as the most recent qualifying stroke? |
| **T4** | Yes → Not a stroke event — same CIPS as last stroke |
| **D5** | Is the code in a valid position for a **subsequent** stroke (as defined in `code_positions_subsequent_stroke_hes_apc`)? |
| **T5** | No → Not a stroke event — code not in valid subsequent position |
| **D6** | Is this episode within the washout period from the last qualifying stroke (as defined in `washout_between_strokes`)? |
| **T6** | Yes → Not a stroke event — within washout period |
| **T7** | No → **Recurrent stroke event** |

Terminal node 0 (T0) is assigned before the loop, to all individuals with no stroke code in any relevant position across all their episodes.

### Part B: ONS deaths algorithm

The ONS deaths algorithm applies the following logic to each death record containing a stroke code:

| Node | Description |
|------|-------------|
| **T0** | No stroke ICD-10 code in any relevant death certificate position → excluded before classification |
| **D1** | Is there a corresponding HES APC record documenting an in-hospital death? (discharge ≤ 1 day from death AND `dismeth = "4"` OR `disdest = "79"`) |
| **T1** | Yes → Excluded — in-hospital death captured by HES APC algorithm |
| **D2** | Is there a qualifying HES APC stroke within `washout_between_death_and_hes_stroke` days prior to death? |
| **T2** | Yes → Excluded — death assumed to relate to prior HES stroke |
| **D3** | Is there ANY prior qualifying HES APC stroke? |
| **D4** | No prior HES stroke: is the code in a valid position for a **first** stroke death (as defined in `code_positions_first_stroke_deaths`)? |
| **T3** | No → Not a stroke event |
| **T4** | Yes → **First stroke event** |
| **D5** | Prior HES stroke exists: is the code in a valid position for a **subsequent** stroke death (as defined in `code_positions_subsequent_stroke_deaths`)? |
| **T5** | No → Not a stroke event |
| **T6** | Yes → **Subsequent stroke event** |

## 5. Inclusion Criteria Applied

### HES APC data (D00a-hes_apc_cleaned.py)
- Valid `epikey`, `person_id`, 'provider code'
- Valid episode and admission dates
- Finished episodes only (`epistat = 3`)

### Study cohort (D01-create_cohort.py)
- Within study age range (18-120 default) at study start
- Known sex
- Alive on study start date
- Valid death records if applicable
- GDPPR registration before study start
- English LSOA

### Stroke algorithm (D02-hes_apc_stroke_algorithm, D03-ons_deaths_stroke_algorithm)
- Episodes within study period (`epistart` between `study_start_date` and `study_end_date`)
- `person_id` is not null
- Inner join to study cohort

## 7. Implementation in GitLab and Databricks within the NHS England SDE

Researchers who wish to run the SCORE-CVD Stroke algorithm within the NHS England SDE can do so using a dedicated branch of the GitLab repository and the project's Databricks workflow.

Using a separate branch allows researchers to make project-specific changes, including changes to the algorithm parameters, while retaining a clear and reproducible record of the version of the algorithm used.

### 7.1 Preparing the Algorithm in GitLab

* In GitLab, navigate to the `hds_ls_score_cvd_stroke` repository.
* Create a new branch for your project. Use a clear, project-specific branch name, for example `<project_name>`.
* The branch should be created from the version of the repository that you wish to use for your analysis.
* Update the parameter values in the `parameters` notebook (`databricks/pipeline/parameters`) to suit your project — e.g. `study_start_date`, `study_end_date`, `stroke_codes`, diagnosis/death-certificate position lists, ICD-10 code truncation lengths, and washout periods (see below), and commit these changes to your branch.
   * This provides a permanent, auditable record of the parameters used to generate your stroke cohort, independent of the Databricks job run history, which may later be removed.
   * Parameters should be changed in the `parameters` notebook rather than directly within the algorithm notebooks.
* If you make any other project-specific changes to the algorithm, commit these to your branch before running the pipeline.

### 7.2 Configuring the Workflow in Databricks

* In the NHS England SDE Databricks workspace, navigate to **Jobs & Pipelines** and open the workflow **`hds_ls_score_cvd_stroke_pipeline`**.
* Open the **Git settings** for the workflow.
   * Change the **Git reference** to the project-specific branch you created in GitLab (e.g. `<project_name>`).
   * Do not change the **Git repository** or **Git provider** settings unless specifically required.
* Check the **Job Parameters** and update them to match your project's requirements.
   * When the pipeline is run as a Databricks workflow, it is the **Job Parameters** that determine the values actually used at runtime, so these should be set to match the values you have committed to the `parameters` notebook, even though the notebook has already been updated. Committing the notebook change gives you a durable record; setting the job parameters ensures the run itself uses the correct values.
* Select **Run Now** to execute the workflow.

The workflow will run the notebooks in the following order:

```
D00-create_table_directory
D00a-hes_apc_cleaned
D00b-hes_apc_cips
D00c_ons_deaths_cleaned
D01-create_cohort
D02-hes_apc_stroke_algorithm
D03-ons_deaths_stroke_algorithm
D04-stroke_algorithm_events
D05-covariates
```

### 7.3 Algorithm Parameters

The algorithm is designed to allow researchers to modify a number of parameters without changing the underlying algorithm notebooks. Parameters should be reviewed before running the pipeline and, where required, modified in the `parameters` notebook (and mirrored in the Databricks Job Parameters, as above).

**HES APC parameters** — control which ICD-10 codes and diagnosis positions are used when identifying strokes in HES APC:

* `stroke_codes` — ICD-10 codes used to identify stroke events (derived from `stroke_subtype_map`).
* `code_positions_first_stroke_hes_apc` — diagnosis positions that can be used to identify the first stroke.
* `code_positions_subsequent_stroke_hes_apc` — diagnosis positions that can be used to identify subsequent strokes.
* `icd10_code_length_hes_apc` — length to which ICD-10 codes are truncated before matching.
* `washout_between_strokes` — minimum period used when determining whether a subsequent stroke represents a new stroke event rather than another episode belonging to the same event.

**ONS deaths parameters:**

* `code_positions_first_stroke_deaths` — positions on the death record that can be used to identify a first stroke death.
* `code_positions_subsequent_stroke_deaths` — positions that can be used to identify a subsequent stroke death.
* `icd10_code_length_deaths` — length to which ICD-10 codes are truncated before matching.
* `washout_between_death_and_hes_stroke` — washout period used to determine whether a stroke death occurs shortly after a qualifying HES APC stroke and should therefore not be counted as a separate stroke event.

**Study period and cohort parameters** — should also be reviewed before running the pipeline, including:

* `study_start_date` and `study_end_date`
* cohort age/inclusion criteria
* stroke ICD-10 code definitions (`stroke_subtype_map`)
* `fatal_stroke_definition` and any other project-specific parameters defined in the `parameters` notebook

### 7.4 Project Configuration

Project-level settings (project name, folder locations, etc.) are controlled by `project_config.json`, which is read automatically by the pipeline's setup notebook (`project_config.py`, in `databricks/pipeline/config/`) at the start of each run. From this, the pipeline:

* Identifies the current user (`username`) and builds a project name unique to that user, in the form `{project_name}_{username_short}`, where `username_short` is your username with the domain removed and dots replaced by underscores (e.g., `joe.bloggs@university.ac.uk` → `joe_bloggs`). This ensures unique table names per user in the shared database.
* Dynamically builds the **project runtime folder** path for that user/project, creating the runtime `config` and `outputs` subfolders if they don't already exist (see Section 10).
* Sets environment variables used throughout the pipeline: `USERNAME`, `PROJECT_FOLDER`, `PROJECT_NAME`, `PROJECT_RUNTIME_FOLDER`, `TABLE_DIRECTORY_PATH`, `TABLE_MAPPING_PATH`.

You should not normally need to edit `project_config.py` itself, it simply reads and applies the values already set in `project_config.json`.

### 7.5 Reproducibility

Where parameters have been changed from the defaults, it is strongly recommended that the modified `parameters` notebook is committed to the project-specific GitLab branch, so that the exact algorithm configuration used to generate the stroke cohort can be reconstructed at a later date.

## 7.6 Pipeline Outputs

The pipeline writes its outputs to the project-specific runtime folder in your own Databricks workspace, plus the derived tables to the shared DSA database.

### 7.6.1 Runtime folder (workspace outputs)

The runtime folder is created automatically (if it doesn't already exist) at:

```
Workspace -> Users -> <your_username> -> hds_ls_score_cvd -> runtime -> config
                                                            -> outputs
```

For example, for user `joe.bloggs@university.ac.uk`:

```
Workspace/Users/joe.bloggs@university.ac.uk/hds_ls_score_cvd/runtime/config
Workspace/Users/joe.bloggs@university.ac.uk/hds_ls_score_cvd/runtime/outputs
```

* The **`config`** subfolder holds the pipeline's internal working files: `table_directory.json` and `table_mapping.json`, used to track which tables have been created and how they map through the pipeline.
* The **`outputs`** subfolder holds the human-readable, project-specific run outputs — for example the decision-tree flowchart CSVs generated by the algorithm notebooks (`flowchart_stroke_hes_apc.csv`, `flowchart_stroke_hes_apc_sdc.csv`, `flowchart_stroke_deaths_default.csv`, `flowchart_stroke_deaths_default_sdc.csv` — SDC versions rounded to nearest 10 for statistical disclosure control). The exact files generated will depend on the notebooks and parameters used for the run. These are not saved to the shared database.

### 7.6.2 Database tables

All derived tables generated by the pipeline (e.g. `hes_apc_cleaned`, `cohort`, `hes_apc_algo_stroke_patients`, `deaths_algo_stroke_patients`, `stroke_events` — see Section 3) are saved to the shared DSA database, prefixed with your unique project name (see Section 9.4), in the form:

```
hds_ls_score_cvd_{username_short}_{table_name}
```

For example, for user `joe.bloggs@university.ac.uk`, the final combined stroke events table would be saved as:

```
hds_ls_score_cvd_joe_bloggs_stroke_events
```

This naming convention ensures that each user's tables remain distinct within the shared database, even when running the same pipeline for the same project.


## 8. Limitations of the Algorithm

The algorithm has been developed using HES APC data - as with all electronic health records, there will be a delay between the patient event and the data being coded and available. This algorithm may not be suitable for all use cases.

NHS administrative data organises records by Hospital Spells and Episodes, each recorded as a single row per patient. An episode is defined as a continuous period of admitted patient care administered under one consultant within one healthcare provider. A stroke occurring after admission will be coded to the start date of the episode, and as such the stroke date may not be accurate to the day of the event.

The washout period between stroke events (default: 30 days) is applied to avoid counting a continuation of the same clinical episode as a new event. This is user-configurable in the `parameters` notebook.

Stroke subtype is assigned using the first stroke ICD-10 code identified per episode. Where a CIPS contains episodes with more than one distinct subtype, the CIPS-level subtype is set to `"unknown"`. Users extending the code list to 4-character codes should update both `stroke_subtype_map` and the diagnosis column positions in `parameters` accordingly.

This algorithm may not be suitable for surgical or intervention trials with short follow-up or where high specificity is required to identify multiple events within a very short period. In these cases a hybrid approach with adjudicated data collection may be more appropriate.
